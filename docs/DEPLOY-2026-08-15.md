# Deploy checklist, 2026-08-15

Everything in this batch: iPhone push wired, three bugs fixed, reminders made
observable. Nothing here is live until the steps below are done, in this order.

## Order matters

1. **SQL first.** Two migrations, both safe to re-run. Supabase dashboard
   (`nwqnakoongrorbwnrqzc`) → SQL editor.
   - `sql/photo-count-computed-columns.sql`
   - `sql/booking-reminders-observability.sql`

   Each file ends with a VERIFY block. Run it and read the output before
   moving on.

   The app has a fallback so pushing the site before running the first
   migration cannot break uploads, but running SQL first avoids the fallback
   ever being used.

2. **Apple key, then secrets.** Full steps in `docs/NATIVE-PUSH-RUNBOOK.md`.
   The short version: Apple Developer → Keys → new key with APNs enabled →
   download the .p8 (once only) → note the Key ID and Team ID → set
   `APNS_PRIVATE_KEY`, `APNS_KEY_ID`, `APNS_TEAM_ID` in Supabase → Edge
   Functions → Secrets.

3. **Deploy three edge functions**, replacing the code with the repo copy:
   - `send-push` ← `supabase/functions/send-push/index.ts`
   - `broadcast-push` ← `supabase/functions/broadcast-push/index.ts`
   - `revenuecat-webhook` ← `supabase/functions/revenuecat-webhook/index.ts`

4. **Push `main`** in GitHub Desktop. That ships the **website and the PWA**.

   It does NOT update the installed native apps. `capacitor.config.json` has
   no `server.url` and there is no live-update plugin, so the native shells
   run a copy of the web assets baked in at build time. Anything in
   `index.html` reaches an iPhone or an Android phone only through a new
   Capawesome build. See "What needs a build" below.

5. **Test**, see below.

## What needs a build, and what does not

| Change | Reaches an installed native app? |
|---|---|
| APNs sender in `send-push` / `broadcast-push` | Yes, server-side |
| `revenuecat-webhook` phone-only fix | Yes, server-side |
| Both SQL migrations | Yes, server-side |
| Client booking-notification fix (`index.html`) | **No, needs a build** |

The old bundled `index.html` still asks for `photos,paused_photos`, which
keeps working because those columns are untouched, so an un-rebuilt app is
not broken by the computed-column migration. It just does not get the saving
until it is rebuilt.

## What changed and why

### iPhone push now works (the headline)

iOS device rows have always held raw APNs tokens, because the app has no
Firebase SDK on iOS. The server sent them to FCM, which cannot deliver to an
APNs token. Every iPhone push failed on the server, not the phone.

`send-push` and `broadcast-push` now talk to Apple directly for `auth='ios'`
rows, with an ES256 JWT signed from the .p8. No app change, no new build, no
store submission. The iOS build already on phones starts receiving pushes as
soon as the secrets are set and the functions are deployed.

The runbook's old iOS instructions (add an iOS app in Firebase, upload the
.p8 there, drop in GoogleService-Info.plist) would not have worked and have
been replaced. The reasoning is written up in the runbook so nobody retries it.

`send-push` also carries the high-priority delivery and error reporting from
the earlier change, so this deploy covers that too.

### Clients booking in the native app never registered for push

`ensureBookingNotifications()` checked the `REQUIRE_NOTIFS_FOR_BOOKING` flag
before it checked whether it was running inside the native app. With the flag
off, which is how it ships, a client booking on a phone fell into the web-push
path, which silently does nothing inside Capacitor. Booking is the moment a
client most needs notifications and it was the one moment that could never
register them. The native check now comes first.

This is a plausible cause of the zero client subscriptions, though not
necessarily the only one. Sign-in already routed clients correctly, so it is
still worth testing both.

### A paying phone-only tech got nothing

`revenuecat-webhook` resolved every lookup path to an email and then wrote
with `.eq('email', techEmail)`. A phone-only tech has no email, so the
subscription applied to no row while the webhook still answered 200 and
RevenueCat considered it delivered. It now resolves to `techs.id` and keys
every write on the id, with phone lookups added to the resolution chain.
This had to be fixed before paid plans come back on.

### Photo uploads stopped downloading the whole portfolio

`loadTechTier()` runs on every upload and selected the entire `photos` and
`paused_photos` JSONB arrays purely to read their lengths. Same pattern on the
admin stats screens, across every tech. They now select `photos_count` and
`paused_count`, PostgREST computed columns that do the counting in Postgres.

### Booking reminders can finally be observed

`_booking_push` calls `net.http_post`, which is fire-and-forget, and it threw
away the request id, so there was no way to tell whether a reminder had ever
gone out. There is now a `push_log` table with a row per push and a
`push_log_recent` view that joins it to the HTTP response while pg_net still
has it.

Found while reading that code: the client fallback key was normalised to
`+1XXXXXXXXXX` but the tech fallback passed `techs.phone` raw, so a tech whose
phone was stored in any other shape got reminders addressed to a key matching
no subscription. Both now go through one `push_identity()` helper that mirrors
the app's `pushKeyFor()`.

## Testing, in the order that isolates failures

**A. iPhone tech push.** Open the app on the iPhone, sign in, accept
notifications, wait for "Notifications are on 💅". That toast means the token
reached `push_subscriptions`. Then fire a probe. `{"sent":1}` means Apple
accepted it; if the phone then shows nothing, the problem is on the device
(Focus mode, per-app notification settings), not the server.

**B. Client push, the one that has never been proven.** Same thing on a client
account: sign in, wait about 4 seconds for the permission prompt, accept, wait
for the toast. Then confirm a row exists:

```sql
select user_id, auth as platform, updated_at from push_subscriptions order by updated_at desc limit 10;
```

Then book an appointment from that client and check the tech's phone buzzes,
and vice versa. Both directions matter.

**C. Reminders.** With a confirmed booking about two hours out:

```sql
select public.process_booking_reminders();
select * from public.push_log_recent limit 10;
```

`status_code` 200 with `{"sent":1}` is a delivered reminder. `{"sent":0,
"reason":"no subscriptions found"}` means the `recipient` string matched no
row, so compare it against `push_subscriptions.user_id`.

**D. Broadcast.** Send an admin broadcast and confirm native devices get it,
not just web.

## Standing gotcha, worth remembering

Reinstalling the app invalidates the old device token, and the server prunes
it on the next failed send. It re-registers automatically, but only when the
app is opened and signed in. So after every store update, a device has to open
the app once before pushes resume. An empty subscription row right after an
update is expected, not a bug.
